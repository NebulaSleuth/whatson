# Whats On — Unified User Model (Vision & Plan of Record)

**Status:** Draft / plan of record. Supersedes the M7 "guest / viewer / binding" model.
**Date:** 2026-07-05
**Grounding:** the capabilities below were verified live against the owner's real
Plex (Plex Pass, Home API), Jellyfin 10.11.8, and Emby 4.9.5.0 servers — see §3.

---

## 1. The problem

Today the app has three overlapping notions of "who is watching":

- **Three subsystem user models** — Plex Home users, Jellyfin users, Emby users —
  each with its own login and library rules.
- **Multiple operating modes** — Whats On Users on/off, the legacy Plex-picker
  path, and (from M7) guest "open/closed" modes.
- **An extra layer** — M7 added *viewers*, *guest memberships*, and device
  *bindings* (`locked` / `locked-new` / `open`).

The result feels disjointed. A person is represented differently in each
subsystem, and "viewer vs user vs guest vs binding" is confusing.

**The vision:** collapse all of it to **one concept — a user (a person).** Whats On
becomes the single identity + access-control layer. The subsystems (Plex,
Jellyfin, Emby) are demoted to **content sources** that Whats On maps users into.
Invites invite *people to become users*, not viewers attached to users.

---

## 2. Core principles

1. **Users are people.** One Whats On user per person. It is the *only* login they
   ever use. No separate Plex/Jellyfin/Emby login for the end user.
2. **Whats On Users is always on.** Remove the enable/disable toggle. The user
   layer *is* the product; there is no "legacy mode."
3. **Whats On owns identity and access.** Per-user library access is a first-class
   concept defined in Whats On. Subsystems are content sources it provisions into.
4. **Go all in on managing users directly** — but *avoid creating subsystem users
   where we don't have to, and always allow mapping to existing ones.*
5. **No viewers, no bindings.** An invited person is simply a user with a scoped
   library set and whichever subsystem mappings the admin granted.

## 3. What we can actually do (verified)

| Capability | Jellyfin 10.11.8 | Emby 4.9.5.0 | Plex |
|---|---|---|---|
| Authenticate as admin | ✅ | ✅ | ✅ (token) |
| List users / libraries | ✅ | ✅ | ✅ (Home users) |
| **Create user** | ✅ `POST /Users/New` | ✅ | ⚠️ Home managed user only (Plex Pass + free slot; cap 15) |
| **Set autogenerated password** | ✅ `POST /Users/{id}/Password` | ✅ | n/a (Home users have no separate pw) |
| **Per-user library access** | ✅ `Policy.EnabledFolders` | ✅ same | ✅ Home restrictions / share sections |
| **New user logs in with generated pw** | ✅ verified | ✅ verified | n/a |
| Delete user | ✅ | ✅ | ✅ (Home) |

**Conclusion:** Jellyfin and Emby support **full lifecycle** (create → generated
password → per-user library restriction → delete), proven end-to-end. **Plex is
the constraint** — see §5.

## 4. The user model

A **Whats On User** is the person:

- `id`, `name`, `avatar`
- `role`: `admin` | `member`  (admin manages users + config)
- Whats On **login credential**: a PIN (TV-friendly) and/or password, stored as a
  **bcrypt hash** (one-way) — this is what the person types.
- Optional **cloud-account link** (email) — only needed for remote onboarding
  (see §8).
- Per-subsystem **mapping + library set** (below).

Each Whats On user maps to **0..1 identity per subsystem** — only the subsystems
the admin wants them to reach:

| Subsystem | Mapping | Managed by |
|---|---|---|
| Jellyfin | `jellyfinUserId` + encrypted access token | **Whats On** (auto-create or map existing) |
| Emby | `embyUserId` + encrypted access token | **Whats On** (auto-create or map existing) |
| Plex | `plexHomeUserId` + per-user token | **Admin** (map to / create a Home user) |

A user need not map to *every* subsystem. Example: an invited friend gets
**Jellyfin only** (auto-created, restricted to "Movies"); Plex stays untouched.

### Library access — defaults + overrides

- The admin sets a **default library set per subsystem** (what a new user gets).
- Any user can have a **per-user override**.
- On invite, the admin picks the library set for that person (defaults prefilled).
- Enforcement is **server-side and real** where possible: Jellyfin/Emby
  `EnabledFolders`; Plex Home managed-user restrictions. Whats On's aggregator
  already scopes shelves to the mapped subsystem identity, so the two agree.

---

## 5. Provisioning strategy per subsystem

**Jellyfin / Emby — full auto-provisioning.**
On "create user" (or invite-accept), Whats On:
1. `POST /Users/New` with the person's name.
2. Generates a strong random password, `POST /Users/{id}/Password`.
3. Authenticates once to obtain that user's access token.
4. Applies the chosen library set via `Policy.EnabledFolders`.
5. Stores the token (and/or password) **encrypted** (see §7).
The person never sees or needs the subsystem password.

**Plex — admin-managed, capped.**
Whats On can only *act as* Plex **Home users** (it needs a per-user token, and the
owner can only mint tokens for Home members — external "shared friends" are out of
scope because we can never hold their token). So per user, the admin either:
- **Maps to an existing Home user**, or
- **Creates a Home managed user** — requires the *admin's* Plex Pass and a free
  Home slot. **Hard ceiling: 15 Home users total** (owner has Plex Pass + 10 free
  slots today).

**Plex without Plex Pass:** no Home / managed users at all → Plex is effectively
**owner-only** on that server. Jellyfin/Emby then carry all multi-user support.
The product must not assume Plex Pass.

---

## 6. Invites — invite a *user* (replaces the M7 viewer/binding model)

Every invite produces a **real Whats On user** (`role: member`). Two flows:

**A. Admin creates, then invites.**
Admin fills in name, avatar, per-subsystem library set, and subsystem mappings.
Whats On provisions Jellyfin/Emby immediately (and maps/creates Plex if chosen).
An invite link is emailed; the person just sets their Whats On PIN/password on
first use.

**B. Invitee self-creates.**
Admin sends an invite carrying the intended library set + which subsystems.
The invitee opens the link, sets name/avatar/credential, and Whats On provisions
the subsystem users **at accept time**.

The invite record carries: `email`, per-subsystem `librarySet`, `subsystems[]`,
`role`, `expiry`. It **no longer** carries `binding` / `viewer` / `newUserName`.

Device onboarding from anywhere (cloud device-code, from M7) **stays** — but it
simply signs the person into their Whats On user and approves the device. There is
no "guest binding."

## 7. Credentials & security

- **Whats On login** (PIN/password): **bcrypt hash**, one-way. What the person types.
- **Subsystem credentials** (generated password + resulting token): **AES-256-GCM
  encrypted at rest** under a backend master key (`.env` / protected key file).
  Reversible on purpose — the backend must decrypt to act as that user against the
  subsystem. This is an **upgrade**: today `plexUserToken` is stored *plaintext* in
  `whatsonUsers.json`.
- **Key management** is the one real risk (a leaked master key decrypts subsystem
  tokens) — same threat surface as today's Plex token, done properly. The master
  key stays on the LAN backend, never in the cloud (the cloud remains "starved").

---

## 8. Cloud account vs Whats On user (a tension to resolve)

M7 introduced a **cloud account** (email + password at whatsontv.net) used to
onboard remote devices. We now also have the **Whats On user** (local profile,
PIN). These must be reconciled:

- **Local-only user:** just a Whats On user with a PIN. No cloud account.
- **Remote-capable user:** the Whats On user is **linked to a cloud account**
  (email + password). Remote device-code onboarding authenticates the cloud
  account, then resolves to the linked Whats On user on the target server.

**Decision needed:** is the cloud account 1:1 with a Whats On user, or can one
cloud account front multiple Whats On users (e.g., a household)? Recommendation:
**1 cloud account ⇄ 1 Whats On user per server** (simplest, matches "users are
people"), with the cloud storing only account↔server membership — no profiles.

---

## 9. What this retires

From the M7 implementation (cloud + backend + mobile), remove/repurpose:

- `GuestMembership.binding`, `guestBinding` (`locked` / `locked-new` / `open`),
  `newUserName`, and the "viewer" language.
- The `guestMode` (open/closed) server setting.
- The device `guestBinding` on `PairedDevice` and the binding-aware branches in
  `userContext`, `provisionDevice`, `redeem-grant`, and the mobile create-profile
  routing. (The create-profile screen itself is **kept** — it becomes the generic
  "set up your Whats On user" screen.)
- The Whats On Users **enable toggle** (always on).
- The legacy `X-Plex-User` picker path (`select-user.tsx`) once Plex mapping runs
  through the unified user model.

An invited "guest" is just a `member`-role Whats On user with a scoped library set.

---

## 10. Migration

- **WO-Users currently OFF:** on upgrade, force on; auto-create an `admin` Whats On
  user mapped to the Plex owner (+ existing Jellyfin/Emby admin if configured), so
  current single-user behavior is preserved.
- **Existing WO users:** keep; backfill `role` (owner → `admin`).
- **Existing M7 guest devices:** map each device's `boundWoProfileId` → its Whats On
  user; drop the binding fields.
- **Plaintext `plexUserToken`:** encrypt in place on first load.
- **Data files:** `whatsonUsers.json` gains per-user library sets + encrypted
  subsystem credential blobs. Cloud invites/memberships drop binding/viewer fields.

---

## 11. Open decisions (settle before building)

1. **Unmapped users** — must a Whats On user map to ≥1 subsystem, or can it exist
   "created now, mapped later"? (Recommend: require ≥1 mapping, or fall back to an
   admin-designated default service so the user sees *something*.)
2. **Cloud account ⇄ Whats On user cardinality** (see §8).
3. **Watched state** — now that subsystem users are real, use subsystem-native
   watched state per mapped user, with Whats On's `tracked.ts` as the unifying
   layer? Or keep Whats On as the source of truth?
4. **Plex-Pass-less servers** — confirm the UX when Plex can't do multi-user
   (Plex owner-only; JF/Emby carry the rest). Detect + message clearly.
5. **Existing subsystem users** — admin UI to *map* a Whats On user to an existing
   Jellyfin/Emby/Plex user vs *create* a new one (both are supported; make the
   choice obvious).

---

## 12. Rough phasing

- **A — User model refactor:** users = people, roles, drop the enable toggle,
  retire viewers/bindings. Migration from current state.
- **B — Subsystem provisioning:** Jellyfin/Emby create+manage+encrypted creds;
  Plex Home mapping/creation UI.
- **C — Per-user libraries:** defaults + overrides; enforce server-side.
- **D — Invites-as-users:** rework the M7 invite flow into the two flows in §6.
- **E — Cleanup + migration:** remove dead M7 concepts; encrypt existing tokens.

Each phase is independently shippable behind the "always-on users" model.
